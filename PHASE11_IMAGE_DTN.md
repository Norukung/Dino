# Phase 11: DTN image messages

Phase 11 keeps the Phase 8 router and Phase 10 relay policy. The router still selects a **messageId** for DIRECT, SMART_SPRAY, WAIT, or SKIP. For `contentType=IMAGE`, the selected message is transferred as one bundle: MESSAGE metadata plus one verified media file. Chunks are transport units, not DTN messages. Text continues to use the original MESSAGE frame and ACK path.

New tests: `Phase11EngineTest.kt` and `Phase11MediaTest.kt`. New schema snapshot: `app/schemas/com.group16.dinoblog.database.DinoblogDatabase/8.json`.

Updated implementation files: `model/Message.kt`, `database/Converters.kt`, `database/DinoblogDatabase.kt`, `database/MessageDao.kt`, `dtn/DtnConfig.kt`, `dtn/DeliveryEngine.kt`, `network/WireProtocol.kt`, `repository/MessageRepository.kt`, `DinoblogApplication.kt`, `viewmodel/AppViewModel.kt`, and `ui/{DinoblogApp,ChatScreen,NetworkDebugScreen}.kt`. Existing migration and wire tests were updated for schema 8 and binary frames. No separate network, preference store, profile sync, or WorkManager was added.

- Room schema 8 adds `messages.contentType`, `messages.mediaId`, and `messages.reservedPeerId`, plus a `media` metadata/resume table. Migration 7→8 is additive. Existing messages default to `TEXT`; receipts, predictability, peers, and routing fields remain intact.
- `messageId` identifies routing, inventory, ACK, and delivery receipts. `mediaId` identifies the binary file. Both UUIDs remain unchanged at relays. `MediaEntity` records MIME, safe display filename, byte size, SHA-256, 128 KiB chunk size, chunk count, 0/1 received bitmap, completion state, source/destination, timestamps, and the small serialized message envelope needed to recover a partial transfer.
- Bytes live in `files/dinoblog_media/<mediaId>.part` until verified, then in `<mediaId>.media`. Only validated UUIDs select paths. The remote filename never selects a path. Neither Room nor JSON stores image bytes.
- A source image is decoded with bounds and sampling, orientation is normalized, its long edge is at most 2048 pixels, and it is flattened to white and JPEG-compressed at qualities 85, 75, 65, 55, then 45 until it is at most 5 MiB. The selected Photo Picker URI is released after the private copy is prepared. JPEG, PNG, and WebP picker inputs are accepted; the transmitted file is JPEG.
- A `MEDIA_MANIFEST` control frame contains the IMAGE MESSAGE envelope and `{messageId,mediaId,mimeType,originalFileName,fileSize,sha256,chunkSize,totalChunks}`. A `MEDIA_ACCEPT` returns missing chunk indices. Existing `MESSAGE_REJECT` conveys `RELAY_DISABLED`, `BUFFER_FULL`, `MEDIA_TOO_LARGE`, `UNSUPPORTED_MEDIA`, `EXPIRED`, `ALREADY_DELIVERED`, `HOP_LIMIT`, or `INVALID_MEDIA`.
- The existing 4-byte length-prefixed JSON frames remain unchanged. A media chunk uses a reserved frame length of `-1`, followed by 4-byte JSON-header length, 4-byte binary length, the JSON header, and exactly that many raw bytes. `MEDIA_CHUNK` identifies messageId/mediaId/chunkIndex. The existing `TcpTransport` session writer mutex serializes both kinds of frames.

## Transfer and lifecycle

1. Source prepares the image, computes SHA-256 and totalChunks, then atomically inserts the IMAGE message and complete media metadata. A chat preview can be cancelled before this insertion.
2. Existing INVENTORY lists the messageId only when its media row is complete. Partial transfers have no complete MESSAGE row and cannot be forwarded or displayed as complete.
3. The Phase 8/10 router chooses a bundle. Sender offers the manifest before sending bytes. Receiver checks identity, MIME, size, expiry, hop boundary, relay consent, free disk, the existing count buffer, and the additional 50 MiB relay-media byte quota.
4. Receiver persists a partial row and deterministic-offset `.part` file. A second carrier with the same messageId/mediaId/SHA-256 may supply missing chunks. Duplicate chunks do not advance the bitmap. The bitmap is written after the corresponding chunk is flushed to disk.
5. When all chunks arrive, receiver checks exact size, SHA-256, and decodable image dimensions; then it renames the file and atomically commits complete metadata and the MESSAGE row. Only then does it send the existing ACK. A final destination also creates the existing message-level Delivery Receipt.
6. A SMART_SPRAY sender reserves its proposed branch before the manifest; the source row's `copiesRemaining` is committed only on the complete-bundle ACK. Rejection restores the reservation. A disconnected image branch retains its durable reservation and may resume with the same peer on a new session. Direct delivery ignores relay opt-out; a local relay opt-out prevents new third-party offers and further spraying of existing carried images.
7. Delivery receipts, expiry, and the existing hop policy trigger relay-only binary cleanup. Source and destination image history is retained. Partial files expire or are removed after a receipt. The 50 MiB relay quota counts both complete and partial media and is released when their metadata is reclaimed. No WorkManager was added; the existing retry/cleanup path handles maintenance.

An active transfer already accepted before a local relay setting change may finish its current bundle. New manifests and new outbound third-party branches re-check the setting. Remote changes take effect on the next HELLO, as in Phase 10.

## Manual device procedure

Use Android phones A, B, C, and D with the same Phase 11 APK. Install with `adb install -r` so a Phase 10 database remains in place. Open Developer → Network Debug to record each Device ID and watch manifest, chunk, ACK, copy, and receipt logs. In Settings, keep **Help carry messages for other users** enabled on relays. Use Developer → Network Debug → **Open chat with Device ID** to address an offline destination.

1. **Direct and text:** Connect A↔D. Send text, then pick a near-5 MiB photo in A's chat, inspect the preview, and send. D must show one verified image; text must retain its normal behavior. Disable relay on D and repeat direct image delivery.
2. **Store-carry-forward:** Disconnect A. Have A queue an image addressed to D. Meet A↔B, then disconnect. Meet B↔D. B should hold one complete relay bundle before the second encounter; D should receive the same messageId/mediaId and issue one Delivery Receipt. The relay file should disappear after B learns the receipt, while A's and D's images remain visible.
3. **Smart spray and consent:** Give B a prior D encounter so its predictability exceeds A's, then meet A↔B with A's image for D. Verify SMART_SPRAY and an unchanged sender copy count until B's complete-bundle ACK. Turn B's relay setting off and repeat with a new image: reject at manifest, send no chunks, and retain A's copies. A can still send its own image through another eligible relay; a previously carried image on B may still go DIRECT to D.
4. **Interruption and restart:** During a large A→B transfer, disconnect after several chunks. B's Debug media row must remain partial, and A's copies must remain unchanged. Reconnect and confirm only missing indices are requested. Repeat with B force-stopped and reopened before reconnecting. For alternate-carrier resume, first arrange that C holds the same complete messageId/mediaId, then have B resume from C after losing A.
5. **Failure and cleanup:** Corrupt a test `.part` file before the last chunk or use the `Phase11MediaTest` hash-failure case; no completion ACK or chat image may result. Fill the relay byte quota, verify preflight `BUFFER_FULL`, then deliver/expire a relay image and confirm the quota falls. Expire a partial transfer and confirm its `.part` file and row are removed. Re-offer a complete image and confirm no chunks or duplicate bubble are created.
